# Taste
- Wants code to run entirely client-side in the browser with no servers — no compilation/runtime backend. Store compiler logic (WASM, in-browser compilation) entirely in the page. Confidence: 0.7
- Prefers to validate new feature work as a standalone unit before integrating it into the consuming app: start with a minimal proof-of-concept (e.g., a single simple HTML page), grow it into a self-contained package, and only wire it into the main app once that piece is publishable — integration is explicitly deferred until then. Confidence: 0.7
- Wants demos/playgrounds to be end-to-end functional — the user's code should actually run and the page should show the program's own output, not intermediate artifacts (e.g., the first lines of generated code). Confidence: 0.7
- Prefers the agent to keep working autonomously through long multi-step implementation/debugging sessions, giving a terse go-ahead directive ("start now", "continue", "continue with engine improvement") and no step-by-step approval rather than re-specifying each step. Confidence: 0.7
- Wants binary/compiler assets built from source via a reproducible, pinned build pipeline (containerized build, pinned upstream version, hashed build receipt) instead of depending on a third-party prebuilt binary. Confidence: 0.5
- Wants the full standard library / real toolchain available to user code rather than a trimmed subset, even at the cost of much larger assets — and judges coverage against the official upstream module index (e.g., modules.vlang.io) rather than a hand-picked sample ("can we get the stdlib to work"). Confidence: 0.75
- Prefers a review-first, gap-enumerating approach: before writing code, study the repo plus its reference/sibling implementation and the consuming app, then produce a concrete list of what is missing ("review it well and see what is missing") and only then fill the gaps. Confidence: 0.6
- Wants release/publish decisions backed by empirical checks on the real artifact (packing the tarball, installing it into a clean throwaway consumer, checking dependency availability) rather than assurances — asks short readiness questions ("are we ready to publish now?") and expects a verified answer. Confidence: 0.55
- Expects problems to be attributed to their proper layer and defects in a third-party dependency fixed upstream in that library rather than worked around locally; keeps only project-specific workarounds in the project. Confidence: 0.7
- When fixing a bug, wants tests written alongside the fix ("do the fix & tests"). Confidence: 0.6
- Wants feature/API parity with the sibling packages in the same family: new capabilities are requested as "similar to `@live-codes/nim-wasm`", and the expectation is to read the sibling's actual API and mirror its shape (same option names like `target`/`emit`, same result field `compiledCode`, same exported constants) instead of inventing a package-specific design. Confidence: 0.65
- Wants build intermediates reachable through the public API as an opt-in (e.g. the generated C as `compiledCode` via a `target: 'c'` mode) so callers can read or take away generated code, with the default path left unchanged. Confidence: 0.5
- Prefers a minimal public API surface: if two options/modes resolve to the same output, delete the redundant one instead of keeping it for symmetry — "if `emit: 'files'` is same as `emit: 'single'` then remove this useless option!" — and expects the whole cluster to go with it (the option, its resolver/constants/aliases, the `compiler.*` accessor, the exports, and the tests/docs that mention it), leaving one canonical result shape. Confidence: 0.7
- Sibling-package parity is a guide for naming/shape, not a mandate to reproduce options that only make sense in the sibling (e.g. copying nim-wasm's `files`/`single` `emit` into a package that emits a single translation unit was rejected). Confidence: 0.6
- Is mindful of the size cost of changes to a published library/package and expects that tradeoff to be measured (e.g., asking "would that increase the library size?"). Confidence: 0.5
- Treats docs as part of the change: expects README (and related docs) refreshed to match new behavior before wrapping up, and wants finished work committed rather than left sitting in the working tree — a directive like "update README and commit" is the expected closing move. Confidence: 0.55
